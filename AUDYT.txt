------------------------------------------------------------
KROK 1: ZORIENTUJ SIE W STANIE PROJEKTU
------------------------------------------------------------

Przeczytaj ten plik od gory do dolu, zwracajac uwage na:

  a) SEKCJA A/B/C - lista wszystkich problemow do naprawienia.
     Kazdy punkt ma numer, opis problemu i gotowy przepis na naprawe.
     Punkty bez oznaczenia [ZROBIONE] = nadal czekaja na realizacje.

  b) SEKCJA D/E/F - lista nowych funkcji do dodania.
     Priorytet: D (wysoki) > E (sredni) > F (niski).
     Punkty bez oznaczenia [ZROBIONE] = nie zostaly jeszcze zaimplementowane.

  c) DZIENNIKI ZMIAN (na poczatku pliku, sekcje "WDROZONYCH ZMIAN") -
     szczegolowy log co, gdzie i jak zostalo juz zrobione.
     Kazdy wpis zawiera nazwe pliku i opis zmiany.

Aby sprawdzic szybko co pozostalo do zrobienia, wyszukaj w pliku fraze
"[ZROBIONE]" i sprawdz jakich numerow brakuje na liscie.

------------------------------------------------------------
KROK 2: WYBIERZ CO ROBIC NASTEPNIE
------------------------------------------------------------

Zalecana kolejnosc pracy (zgodna z sekcja "KOLEJNOSC NAPRAW"):

  Tydzien 1-2:  Sekcja A - Krytyczne bledy (numery 1-5)
  Tydzien 3-4:  Sekcja B - Powazne bledy + refactoring (numery 6-15, 23-24)
  Miesiac 2:    Sekcja D - Nowe funkcje priorytet wysoki (numery 36-40)

------------------------------------------------------------
KROK 3: WPROWADZ ZMIANY
------------------------------------------------------------

Opcja A - samodzielnie:
  1. Przeczytaj opis problemu i sekcje "Jak naprawic" wybranego punktu.
  2. Otwierz wskazany plik w edytorze.
  3. Wprowadz zmiane zgodnie z opisem (stary kod -> nowy kod).
  4. Przetestuj ze zmiana dziala.
  5. Przejdz do Kroku 4.

Opcja B - przez Claude:
  1. Wklej do czatu: "pracujesz w [sciezka projektu], wykonaj poprawki
     z audytu: [numery punktow, np. 16, 17, 19]"
  2. Claude przeczyta pliki, wprowadzi zmiany i opisze co zrobil.
  3. Przejrzyj wprowadzone zmiany (git diff lub podglad plikow).
  4. Przejdz do Kroku 4.

Opcja C - cala sekcja naraz:
  "wykonaj kolejne poprawki i updaty" - Claude sam wybiera co zrobic dalej,
  wprowadza zmiany i aktualizuje ten plik.

Uwagi praktyczne:
  - Zmiany w prisma/schema.prisma wymagaja uruchomienia migracji:
      npx prisma migrate dev --name [nazwa-migracji]
  - Zmiany wymagajace nowych pakietow NPM sa oznaczone w opisie
    ("npm install ...") - zainstaluj je przed uruchomieniem aplikacji.

[ZROBIONE] POPRAWKA 30 (REWIZJA) - CRASH MIDDLEWARE / ClientFetchError NextAuth
  Plik: src/middleware.ts
  Problem:
    Poprzednia implementacja middleware importowala `auth` z src/lib/auth.ts.
    Ta funkcja importuje Prisma Client i bcryptjs — oba pakiety sa niekompatybilne
    z Edge Runtime (w ktorym Next.js wykonuje middleware).
    Skutek: middleware crashowal przy KAZDYM requesce, Next.js zwracal HTML (500),
    SessionProvider dostawal HTML zamiast JSON z /api/auth/session i rzucal:
      ClientFetchError: Unexpected token '<', "<!DOCTYPE "... is not valid JSON
    Aplikacja byla calkowicie niezdatna do uzycia.
  Naprawa:
    Zamieniono import `auth` z lib/auth.ts na `getToken` z `next-auth/jwt`.
    getToken czyta JWT bezposrednio z cookie bez zadnych zaleznosci Node.js
    i dziala poprawnie w Edge Runtime.
    Zachowanie jest identyczne — niezalogowani uzytkownicy sa przekierowywani
    do /login?callbackUrl=... przy probach dostepu do /dashboard i /settings.

      export function haversineMeters(
        lat1: number, lon1: number,
        lat2: number, lon2: number
      ): number {
        const R = 6371000;
        const toRad = (d: number) => (d * Math.PI) / 180;
        const dLat = toRad(lat2 - lat1);
        const dLon = toRad(lon2 - lon1);
        const a =
          Math.sin(dLat / 2) ** 2 +
          Math.cos(toRad(lat1)) * Math.cos(toRad(lat2)) * Math.sin(dLon / 2) ** 2;
        return R * 2 * Math.atan2(Math.sqrt(a), Math.sqrt(1 - a));
      }
